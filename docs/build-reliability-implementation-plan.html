Priority 3 · Existing search contract

3. Clarify and correct the existing search tool

Decision: retain term/query, existing filters, and explicit sorting. Do not add discovery/exact modes, offer grouping, performance ranking, or restrictions on legitimate comparisons.

Verified from code

  • The repository trims the term and applies name LIKE %term% OR normalized_name LIKE %term%. This is substring matching, not an exact identity lookup or automatic token/alias expansion. The tool does not normalize punctuation or spacing in the input term.
  • Ascending price works for finding cheaper matching listings; descending price returns expensive matches first. Current schema guidance incorrectly calls descending price “best part within the budget first” and restricts ascending order to explicit cheapest-option requests.
  • Registry filters such as DDR, socket, and minimum wattage run after the SQL query. The final count uses only the SQL predicates, so total_matching and has_more can overstate the filtered result set.
  • The repository supports offset, but the tool schema does not expose it. Existing callers must refine terms/filters to explore omitted matches; do not advertise accessible pagination that does not exist.
  • The schema defaults to eight results, but direct searchProducts() calls with no limit omit that default and reach the repository default of 20. This is a per-response contract issue, not a limit on the number of searches.

Implementation

  1. Correct descriptions: price order describes price only; the model may use ascending order to compare affordable offers without explicit user wording. Explain substring matching and that similarly named variants may also match.
  2. Test existing term and query-alias behavior with representative names and spacing variations. Keep the current matching semantics unless a demonstrated failure needs a narrow fix; do not introduce fuzzy identity matching.
  3. Make filtered counts accurate, or explicitly distinguish a SQL candidate count from the final filtered count. Compute has_more from additional eligible matches rather than the unfiltered count. Choose a method that does not force full-catalog spec resolution on every search just to show a count.
  4. Enforce the existing eight-result default consistently for schema-driven and direct calls. Preserve the existing per-response maximum and permit further searches.
  5. Keep refinement hints truthful. The model can compare categories, specific terms, platforms, variants, and prices as extensively as useful. No forced selection after a fixed number of searches.

Code areas: search schema/helper, catalog repository count/filter logic, compact result types and tool descriptions.

Acceptance: terms and aliases follow documented matching; explicit ascending/descending sorting works; price is never labeled a performance rank; counts and has-more remain truthful with registry filters; direct calls use the same default as tool calls. No new search modes or deduplication are introduced.

Priority 5 · Error-message fix only

5. Show accurate provider error messages

Problem: an explicit daily-quota error currently tells the user to “wait a moment,” which implies a short cooldown. Fix the existing error formatting without adding quota infrastructure.

  1. Recognize explicit daily-quota exhaustion in the error response and distinguish it from temporary rate limiting. HTTP 429 alone does not identify which limit was reached.
  2. Show retry or reset information only when supplied in the response. Otherwise leave the timing unknown. Do not infer context overflow from HTTP 400.
  3. Keep a useful generic message when the provider does not identify the cause. Preserve bounded, sanitized details using the existing error presentation.
  4. Reuse existing error helpers and settings links. Do not add quota polling, quota endpoints, usage meters, account-balance integrations, or automatic model switching.
The provider reports that its daily free-model quota is exhausted. Try again after it resets, or check your provider settings.

Code areas: existing chat API error extraction/sanitization, src/lib/format.ts, and existing error display only where needed.

Acceptance: the exported daily-quota error no longer says “wait a moment”; an unspecified 429 retains generic rate-limit guidance; supplied retry/reset details are shown accurately; sensitive details are redacted. Extend existing error-format tests with these cases.
